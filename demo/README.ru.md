# Стенд проверки восстановления

[English](README.md)

## 1 Назначение

Небольшое открытое демо работает с PostgreSQL и контрольным файлом. Посетители могут только читать данные. Страница показывает площадку, записи базы и согласованность файла. Доступность страницы сама по себе не доказывает наличие резервной копии. Общая система RolyPolyOps пока не реализована.

Демо можно запустить на двух серверах Linux. Хранилище restic на другой площадке принимает зашифрованные копии основной. После подтвержденного переключения нужно настроить копирование с новой основной площадки на другой сервер. Здесь две области отказа: потеря сервера хранения одновременно лишает нас его резервного приложения и хранилища. Для важных данных нужно отдельное хранилище у другого провайдера.

## 2 Запуск нового демо

Нужны Docker с правами root, Compose v2, Python 3, curl, openssl, util-linux и restic. Версии испытательного стенда: Docker 29.1.3, Compose 2.40.3, PostgreSQL 17.11, restic 0.16.4/0.18.1, Ubuntu x86_64. Базовые образы закреплены контрольными суммами; зависимости npm имеют файл зафиксированных версий.

Скопируйте этот каталог в отдельное место, например `/opt/rolypolyops-lab`, и выполните из него:

```sh
sudo ops/init-demo A       # на второй площадке укажите B
curl --fail http://127.0.0.1:8080/healthz
```

При наличии базы или учетных данных инициализация откажется от запуска. Порт приложения доступен только локально. Для публикации нужен обратный прокси с HTTPS. Порт PostgreSQL наружу не открывается. Открытые адреса принимают только GET и HEAD и возвращают исключительно искусственные тестовые данные.

## 3 Хранилище и учетные данные

На сервере хранения создайте `/var/lib/rolypolyops/repository` и файл `.htpasswd` с хешем bcrypt для пользователя `lab`. Исходный пароль доступа храните отдельно. Запустите хранилище командой `docker compose -f storage.compose.yaml up -d`. Оно слушает `127.0.0.1:8000`, требует пароль и разрешает удаленному клиенту только добавление копий.

Пример маршрута Caddy внутри блока HTTPS-сайта сервера хранения:

```caddy
handle_path /backup/* {
    reverse_proxy 127.0.0.1:8000
}
```

Создайте случайный сложный пароль шифрования restic, отличный от пароля HTTP. Сохраните его как `/etc/rolypolyops/repository-password` с владельцем root и правами 0600 на обоих серверах, а также в отдельном защищенном комплекте восстановления. Потеря этого пароля делает восстановление невозможным. Закрытая конфигурация должна оставаться вне репозитория.

Установите `ops/labctl` как `/usr/local/sbin/rolypolyops-lab`. Создайте `/etc/rolypolyops/lab.env` с владельцем root и правами 0600:

```sh
RPO_ROOT=/opt/rolypolyops-lab
RESTIC_REPOSITORY=rest:https://backup.example.org/backup/primary
RESTIC_PASSWORD_FILE=/etc/rolypolyops/repository-password
RESTIC_REST_USERNAME=lab
RESTIC_REST_PASSWORD=REPLACE_WITH_A_SEPARATE_RANDOM_HTTP_PASSWORD
```

Для восстановленной основной копии дополнительно укажите `RPO_ROOT` с каталогом ее сервиса, `RPO_PROJECT` с именем проекта Compose, `RPO_SOURCE_PORT` с локальным портом и `RPO_SOURCE_LABEL` с обозначением площадки. На сервере восстановления `RPO_TARGET_LABEL` задает обозначение восстанавливаемой копии.

На сервере хранения для локальной проверки и восстановления укажите `RESTIC_REPOSITORY=/var/lib/rolypolyops/repository/primary`. Один раз инициализируйте хранилище с исходного сервера: `sudo rolypolyops-lab init`. Запрос к маршруту хранения без пароля должен получать HTTP 401.

## 4 Копирование и восстановление

```sh
# исходный сервер
sudo rolypolyops-lab backup
sudo rolypolyops-lab status
# сервер восстановления
sudo rolypolyops-lab verify
sudo rolypolyops-lab restore-check latest
sudo rolypolyops-lab restore-standby latest
```

При создании копии останавливается веб-процесс демо, сохраняется логическая копия PostgreSQL и соответствующие ей файлы, пароль приложения и описание Compose. Затем веб-процесс запускается снова. Экспорт образов и зашифрованная передача выполняются после этого. Останавливается только известный процесс записи этого демо; способ не подходит приложению с другими источниками записи.

Копия содержит точные идентификаторы и сохраненные образы приложения и базы, контрольные суммы и ожидаемые значения записей. Восстановление использует новый каталог, отдельный проект Compose и локальный порт 18081 для проверки либо 18080 для сохраняемого резерва. Сценарий загружает сохраненные образы, восстанавливает базу и сравнивает значения записей, SHA-256 файла, ответ HTTP, версию, идентификаторы образов, пути новых подключений файлов и ограничения среды исполнения. Исходный Compose воспроизводит эти ограничения. Работающие данные исходной и целевой площадок не перезаписываются.

`restore-check` после проверки удаляет свои временные контейнеры, сети и каталог. При ошибке очистки каталог сохраняется для расследования, а операция считается неуспешной. `restore-standby` оставляет проверенную копию и записывает ее расположение в `/var/lib/rolypolyops/standby.json`. Перезапись существующей записи резерва запрещена. Подготовленная копия автоматически основной не становится.

## 5 Расписания и наблюдение

Установите службу и таймер копирования из `ops/` на исходный сервер, а службу и таймер проверки восстановления на целевой сервер в `/etc/systemd/system/`. Выполните `systemctl daemon-reload`, затем включите соответствующий таймер через `systemctl enable --now`. Копии создаются каждый час; полная проверка хранилища и пробное восстановление выполняются ежедневно. До использования расписания запустите каждую службу вручную хотя бы один раз.

`rolypolyops-lab status` показывает копии, таймеры и последние успешные операции. Ошибки доступны через `systemctl --failed` и `journalctl -u rolypolyops-backup -u rolypolyops-restore-check`. Внешних уведомлений пока нет. Старая успешная запись не подтверждает успех последнего запуска по расписанию.

Удаленный клиент с правом добавления не может очищать историю. Удаление старых копий должно выполняться отдельно на сервере хранения после проверки пригодных точек восстановления. Автоматическая очистка на стенде отключена; нужно контролировать свободное место и не допускать заполнения диска.

## 6 Управляемое переключение и ограничения

Перед публикацией восстановленной копии остановите исходное приложение и отключите его автоматический перезапуск. Подтвердите выбранную копию и допустимую потерю данных, проверьте целевую площадку, затем переключите трафик. Исходные данные сохраните для расследования. Изменение DNS не останавливает старые процессы записи. После новых записей нельзя возвращаться к прежней базе без отдельного плана согласования данных.

На стенде нет репликации базы, большинства голосов, внешнего отключения площадки, учетных данных Cloudflare, автоматического переключения DNS и возврата, подключения произвольных сервисов и графического управления. Открытое демо работает только на чтение. Управляемая остановка приложения не доказывает восстановление при полной аварии хостера или разделении сети.

Сторонние компоненты сохраняют свои лицензии: [restic](https://github.com/restic/restic), [rest-server](https://github.com/restic/rest-server), [PostgreSQL](https://www.postgresql.org/about/licence/), [Node.js](https://github.com/nodejs/node/blob/main/LICENSE), [Caddy](https://github.com/caddyserver/caddy). Код DockNest и BackupSheep в инструменты стенда не включен.
