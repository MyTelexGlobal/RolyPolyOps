# Контракт сервисов Compose и хранилищ, версия 2

[English](compose-v2.md)

Статус: контракт реализации 0.2.0. Возможности требуют приемки до выпуска. Существующие API тестового приложения сохраняют совместимость. Контракт описывает поведение продукта.

Редакция контракта: 3, с уточнениями принятой редакции 2, без новых заявлений о готовности. Неоднозначности прежних вариантов разрешаются правилами ниже. Идентификаторы полей, коды и форматы в этом переводе совпадают с английским контрактом.

## 1 Результат для владельца и границы

Владелец выбирает существующий проект на подключенном сервере Linux Docker, через мастер подключает выделенный репозиторий restic, сохраняет настройки, окружение, образы и постоянные данные, затем восстанавливает точный снимок как новый проект на другом подключенном сервере. Не нужны lab.env, написанные вручную адаптеры, команды базы данных и подготовка целевого каталога. Мастер завершается только после настоящей копии, соответствующего восстановления и наблюдаемого расписания сервиса. Несколько сервисов и репозиториев имеют разные идентификаторы и истории.

Базовые требования: Linux Docker 29+ с правами root, Compose 2.24+ с каноническим JSON, restic 0.16+, Python 3.11+, cryptography 41+ на агентах. Служба управления использует только стандартную библиотеку. Установщик проверяет зависимости. На поддерживаемых Ubuntu/Debian он может установить отсутствующие restic/python3-cryptography и Docker/Compose только при их отсутствии, без перезапуска или замены существующих развертываний. Другие системы получают точную ошибку требований. Ложное состояние подключения запрещено. Подключение по токену остается единственным этапом установки с привилегиями.

Поддерживается целый локальный проект Compose: он работает, у каждого включенного сервиса один контейнер, используются обычные локальные именованные тома, подключения файлов или каталогов с данными и настройками, файловые configs/secrets, разрешенное окружение запуска, уже собранные локально доступные образы и обычные сети bridge. При сохранении все контейнеры корректно останавливаются на ограниченное время, данные копируются в неизменяемый локальный промежуточный набор, возобновляется именно ранее работавший набор контейнеров, затем загружается зашифрованная копия. Перерыв раскрывается перед подтверждением. Логические выгрузки уровня приложения и работа без простоя не заявляются.

До остановки отклоняются: privileged, host PID/IPC/network, устройства, добавленные capabilities, опасные параметры безопасности, сокет Docker и подключения для управления сервером, внешние сети, анонимные тома и удаленные драйверы, volume driver_opts, реплики, неразрешенные зависимости или подстановки, неподдерживаемые исполняемые поля модели, неизвестные внешние писатели и изменение конфигурации. Поддерживаются обычный root в контейнере, read_only, cap_drop, no-new-privileges, user/group, command, entrypoint, environment, healthcheck, ограничения ресурсов, depends_on, подключения только для чтения и сведения о локальной сборке. Build удаляется из производного описания запуска, сохраняются точные идентификаторы работающих образов. При восстановлении нет сборки и загрузки образов из сети. Созданный продуктом восстановленный проект нельзя зарегистрировать как посторонний источник до его активации или принятия владеющим сервисом.

Владелец подтверждает самодостаточность проекта и отсутствие писателей вне его контейнеров. Агент дополнительно отклоняет пересечения подключений с контейнерами другого работающего проекта. Процессы самого сервера надежно обнаружить нельзя. Это допущение показывается явно и не выдается за проверенный факт.

## 2 Повторное использование и изоляция

Используются существующие аутентификация, CSRF/Origin, SQLite, планы и задания, идемпотентность по UUID, nonce, экземпляр агента, индекс увиденных операций, блокировки неизвестного результата и сверка фактического состояния. Вторая очередь не создается. Исходный тестовый профиль, таймеры, данные, маршруты интерфейса и восстановление сохраняются.

Новые постоянные сущности: хранилище, подключение хранилища к серверу, сервис Compose и восстановление. Каждое общее задание связано с serviceId/storageId/restoreId по назначению. В этом выпуске сохраняется общая последовательная обработка. Зависимости выражаются родительскими и дочерними заданиями. Дочернее нельзя отправить до успеха родителя или считать успешным из-за его отсутствия. Ошибка родителя закрывает неотправленное дочернее задание как status `failed`, stage `cancelled`, error `parent_failed`. Неизвестный родитель закрывает его как status `failed`, stage `blocked`, error `parent_unknown`. Автоматического повторного добавления в очередь нет, даже после успешной сверки родителя. Владелец явно запрашивает новую последовательность. Неразрешенный родитель сохраняет общую блокировку неизвестного результата.

Общее состояние агента хранится в managed/ его каталога состояния, кроме модулей systemd и временных вспомогательных ресурсов. Отдельные испытательные экземпляры используют отдельное состояние. Данные доступа к реестру, полные разрешенные модели Compose, закрытые ключи и секреты хранилища доступны только root на соответствующих серверах. Их нет в SQLite панели, HTTP-ответах, квитанциях и журналах. Панель хранит только ограниченные очищенные сведения и зашифрованные пакеты учетных данных.

## 3 Обнаружение, учетные данные и хранилище

Состояние агента добавляет `compose` с `ready`, `error?`, `key:{id,publicKey,algorithm}`, `projects`, `storages`, `services`, `restores`, `addresses`. publicKey: base64 DER SubjectPublicKeyInfo; id: его SHA256 строчными буквами; algorithm: `RSA-OAEP-256+A256GCM`. Проект содержит `id` (имя проекта Docker), `name`, `fingerprint` (64 шестнадцатеричных знака), `supported`, `reasons:[stable_code]`, `services:[{name,imageId,healthcheck,ports:[integer]}]`, `mounts:[{kind,target,label,readOnly}]`, estimatedBytes и architecture. Значения разрешенного окружения и содержимое секретов сервера не передаются. Addresses содержит маршрутизируемые IP для показа итогового адреса. Ограничения: 20 проектов, 20 контейнеров на проект, 100 подключений на проект, 20 сервисов на сервер и 8 репозиториев. Превышение явно не поддерживается.

Обнаружение читает настоящие метки Compose с упорядоченными файлами конфигурации и каталогом проекта, сравнивает сформированную модель с фактическими контейнерами, подключениями и образами. Команды используют фиксированный локальный сокет Docker, явные файлы Compose и проект. Запрещены source/eval файлов окружения приложения и доверие их COMPOSE_*/DOCKER_*. Отпечаток связывает каноническую разрешенную модель, идентичность контейнеров, идентификаторы образов и байты входных configs/secrets; изменяемые данные приложения исключены. Регистрация и каждое сохранение проверяют отпечаток до остановки. Изменение проекта требует видимого повторного импорта или обновления владельцем. Автоматическая перепривязка запрещена.

Типы хранилища: `rest`, `s3`. Открытые сведения: `{id,name,kind,endpoint,bucket?,prefix?,region?}`. Endpoint является адресом HTTPS с проверкой сертификата, без userinfo, запроса, фрагмента и управляющих символов. REST задает точный URL репозитория без `rest:`. S3 задает origin HTTPS, проверенный бакет и относительный префикс. Локальные, файловые, SSH и командные способы хранения в этом выпуске отсутствуют. Учетные данные REST: username/password. S3: accessKeyId/secretAccessKey и необязательный sessionToken. repoPassword независим. Допустимы только общедоступные адреса TLS. Loopback, link-local, частные, multicast, неопределенные и служебные адреса метаданных отклоняются. CONNECT-прокси для точного origin разрешает и закрепляет каждое соединение за допустимым общедоступным IP, отклоняет другие узлы назначения, включая перенаправления, и оставляет сквозную проверку сертификата restic. Пустой NO_PROXY исключает обход. Отключение TLS и правка /etc/hosts запрещены.

Агент создает постоянный ключ RSA-3072 при первом использовании с доступом только root. Переустановка сохраняет его. Для каждого пакета браузер создает новый ключ AES-256-GCM и IV из 12 байт, оборачивает ключ через RSA-OAEP SHA256/MGF1-SHA256 и использует тег GCM в 128 бит. Применяются cryptography на агенте и WebCrypto в браузере. Собственные реализации AES/RSA запрещены. Пакет:

`{v:1,algorithm:"RSA-OAEP-256+A256GCM",nodeId,keyId,storageId,requestId,bindingGeneration,mode,expiresAt,wrappedKey,iv,ciphertext}`

Все двоичные поля используют стандартный base64. AAD: канонический UTF8 JSON с отсортированными ключами и компактными разделителями для `{v,nodeId,keyId,storageId,requestId,bindingGeneration,mode,expiresAt,purpose:"storage"}`. Wrapped key: 384 байта, IV: 12 байт, открытый текст AES: не более 16 КиБ. ExpiresAt выдает панель в UTC ISO, не более чем на 15 минут вперед. Срок проверяется при принятии агентом, а не только при постановке в очередь. Просроченное в очереди дочернее задание завершается `envelope_expired`, мастер получает новый запрос и шифрует заново. Сверка читает надежно записанное локальное намерение и доказательство подключения, не нуждается в пакете и не расшифровывает его заново. Открытое содержимое: `{metadata,repoPassword,credentials,bindingGeneration,requestId,mode}`. Оно точно совпадает с одобренными панелью metadata. RequestId является UUID, сохраняемым в принятой агентом записи подключения и версии. BindingGeneration выдает панель: положительное монотонно растущее число на пару хранилище/сервер. Агент отклоняет старое поколение и использованный requestId; квитанция того же задания может проверяться без повторного применения. Панель отклоняет устаревший запрос. Старшая версия заменяет конфигурацию только по явно разрешенному connect без незавершенной работы старого подключения. Параметры окончательных заданий и планов очищаются от пакета, остаются его хеш и безопасные сведения о намерении. Надежная квитанция того же запроса сверяется без повторной инициализации. Открытых секретов нет в localStorage/sessionStorage/IndexedDB и постоянном состоянии панели. Интерфейс удерживает их только на время мастера, предлагает локальный комплект восстановления и удаляет после завершения или выхода.

Владелец выбирает `create` или `attach`. Attach проверяет идентичность и пароль репозитория и никогда не инициализирует. Create сначала положительно доказывает отсутствие конфигурации репозитория и пустоту выделенного места: известные ресурсы REST или подписанный S3 ListObjectsV2. Ошибки аутентификации, TLS, бакета, передачи и списка не означают пустоту и никогда не разрешают init. Доказательство пустоты и намерение инициализации записываются надежно до restic init. Неизвестный результат init принимается только после проверки attach пароля и repositoryId относительно именно записанного намерения; иначе остается неизвестным. Reset/unlock/prune/forget и удаление существующих объектов запрещены. Create использует отдельное уникально обозначенное место, показанное до подтверждения. Постороннее заполненное место отклоняется. Первое подключение источника создает репозиторий, остальные подключаются к точному возвращенному repositoryId. Сверка проверяет локальное доказательство, не повторяет init вслепую. Ошибка пароля, TLS, бакета и прав явно завершает подключение ошибкой. Новые получатели используют тот же мастер и шифрованные данные, без ручной правки файлов на сервере.

## 4 API продукта

Все маршруты наследуют вход, обязательную смену пароля, точный Origin, CSRF, ограничения JSON, устойчивые коды ошибок и правила редакций. API возвращает только открытые сведения. Клиент сохраняет идентичный запрос для повтора с его UUID. Конфликтующее повторное использование дает 409. Новые действия и области проверяются панелью и повторно агентом.

GET `/api/overview` добавляет `storages`, `services`, `restores`; состояние узла добавляет очищенный объект `compose`. Существующие ключи сохраняются. Состояние хранилища показывает repositoryId, подключения каждого сервера и ошибки. Сервис показывает sourceNodeId, projectId/fingerprint, storageId, backupInterval, setupState, latestBackup/latestRestore, фактическое расписание и область проверки здоровья. Снимки связаны с serviceId и repositoryId, а не с произвольным сообщившим сервером. Восстановления показывают id, serviceId, snapshotId, nodeId, state (`isolated_ready`, `active`, `failed`, `outcome_unknown`), проверки и фактические соответствия портов.

POST `/api/storages`: `{id,name,kind,endpoint,bucket?,prefix?,region?,expectedRevision,idempotencyKey}`. Создает только открытые сведения. Id является клиентским UUID для привязки пакетов до загрузки. POST `/api/storages/{id}/prepare`: `{sourceNodeId,nodeIds,mode:"create"|"attach",expectedRevision,idempotencyKey}`. Возвращает сохраняемый запрос с ограниченным сроком: `{requestId,expiresAt,metadata,bindings:[{nodeId,key,mode,bindingGeneration}]}`. Только источник может создавать. Получатели подключаются после доказательства идентичности репозитория источником. Интерфейс шифрует каждое подключение по этому запросу. POST `/api/storages/{id}/connect`: `{requestId,bindings:[{nodeId,envelope}],expectedRevision,idempotencyKey}`. Создает сохраняемую последовательность с первым родителем и возвращает `{jobs,storage}`. Одно явное подтверждение мастера охватывает эти подключения. Позднее можно добавить серверы. Успешные подключения сохраняются, кроме отдельного разрешенного запроса на их замену. У заменяемого подключения не должно быть незавершенной работы.

POST `/api/services`: `{id,name,sourceNodeId,recoveryNodeId,projectId,fingerprint,storageId,backupInterval,exclusiveWriters:true,healthCheck?:{service,port,path,expectedStatus},expectedRevision,idempotencyKey}`. Создает сервис и `compose-register`, возвращает `{service,job}`. Хранилище уже подключено к источнику и выбранному получателю. Name является ограниченным обычным текстом, идентификаторы являются UUID, interval: 15min/hourly/daily. ProjectId/fingerprint должны соответствовать свежему поддерживаемому обнаружению. HealthCheck допускает только HTTP, без URL, host, заголовков и команд оболочки; service принадлежит проекту, port 1..65535, относительный path начинается с / без управляющих символов, expectedStatus 100..599. Сформированная конфигурация и секреты не приходят из браузера. Обновление использует тот же явный импорт с текущей expectedRevision и без активной работы. Незаметная перезапись регистрации запрещена.

Общие операции используют существующие POST `/api/plans`, POST `/api/jobs`, GET `/api/jobs/{id}`. Параметры содержат serviceId и область, без текста команд оболочки:

- `storage-configure`: внутренние задания подключения, `{storageId,metadata,envelope,mode,expectedRepositoryId?}`.
- `compose-register`: внутренний импорт, `{serviceId,projectId,fingerprint,storageId,backupInterval,exclusiveWriters,healthCheck?}`.
- `compose-backup`, `compose-verify`: источник либо допустимый подключенный сервер соответственно, `{serviceId,storageId}`. Verify выполняет полный `restic check --read-data` связанного репозитория, не заявляет правильность приложения и не создает снимок.
- `compose-restore`: выбранный подключенный получатель, точный канонический snapshotId верхнего уровня и `{serviceId,storageId,snapshotId}` с равными идентификаторами снимка. Сохраняет отдельную изолированную копию, restoreId равен jobId.
- `compose-remove`: `{serviceId,restoreId}`. Удаляется только изолированная собственная копия. Активная копия этим действием не удаляется.
- `compose-schedule`: только источник, `{serviceId,interval}`. Сохраняет и применяет таймер systemd конкретного сервиса, не старый таймер тестового приложения.
- `compose-stop`: внутренняя остановка источника при явной активации, `{serviceId,fingerprint}`.
- `compose-activate`: внутреннее задание получателя после успешной остановки, `{serviceId,restoreId,sourceStopJobId,interval,ports:[{service,target,published,hostIp,protocol:"tcp"}],allowEgress:true}`.

POST `/api/services/{id}/complete`: `{restoreId,expectedRevision}`. Требует регистрацию источника, свежие подключения, свежую успешную compose-backup и соответствующее восстановление точного снимка на выбранном другом сервере с обязательными проверками данных, образов, запуска и здоровья, фактически включенный таймер нужного интервала и отсутствие активных, неизвестных и изолированных для расследования операций. Приложение без проверки здоровья показывается как запущенное, но непроверенное, без полной готовности. Область здоровья явная: Docker health/HTTP. Правильность произвольных бизнес-данных базы не заявляется.

POST `/api/services/{id}/activate`: `{restoreId,ports,allowEgress:true,acceptSnapshotLoss:true,expectedRevision,idempotencyKey}`. После явного подтверждения плана создает остановку источника, затем активацию получателя, возвращает `{activationGroupId,jobs}`. Допустима только успешно восстановленная изолированная копия этого сервиса. План показывает snapshotTime, возраст и окно потери данных; требует `acceptSnapshotLoss:true`. Изменения источника после выбранного снимка отсутствуют на получателе. Это историческое восстановление, без переноса последних изменений. Свежесть данных означает проверку байтов относительно снимка до первого запуска приложения. Обычные записи при запуске далее не выдаются за тождественные байты копии. Это управляемый владельцем перенос. Источник должен быть на связи, доказательство остановки реально. Недоступный источник отклоняется. До остановки отключается исходный таймер и исходным политикам restart задается `no`. Активация сохраняет свежие данные, использует только выбранные свободные порты TCP, разрешает запрошенные исходящие подключения, не присваивает внешние общие ресурсы сервера. При подтвержденной активации тот же сервис и история репозитория переходят к получателю: он регистрирует созданный собственный проект, становится источником и включает свой таймер. Немедленно выполняется первая копия нового источника. Защита после переноса подтверждается только при ее успехе. Работающий получатель с ошибкой копирования получает `active_unprotected` и сохраняет полномочия нового источника. Он не показывается как полностью защищенный. Повтор копирования или настройки идет через панель, старый источник не возобновляется. Старый источник остается остановленным с отключенным таймером. Неизвестная или частичная активация никогда автоматически не возобновляет источник. Cloudflare/DNS, маршрутизация Caddy, отключение провайдера и автоматический возврат не входят в операцию. Показываются настоящие IP/порт и ограничение: внешний межсетевой экран, TLS и DNS находятся вне операции.

Существующий POST `/api/jobs/{id}/reconcile` проверяет точные журналы и ресурсы общей операции. Исходное изменение не повторяется только из-за утраченной квитанции. Блокировки неизвестных операций и отсутствующих в каталоге результатов распространяются на общие и тестовые действия. Проверка потерянных операций использует общую область при ее наличии и не применяет к ней правила очистки тестового приложения.

До отправки активации панель проверяет надежную успешную запись остановки с совпадающими serviceId, отпечатком источника, назначенным экземпляром и sourceStopJobId. Это предполагает нескомпрометированную панель. Время снимка и принятие потери данных неизменяемы в плане. UDP/SCTP не поддерживаются. Каждое опубликованное соответствие выбирает владелец.

POST `/api/services/{id}/resume-source`: `{activationGroupId,expectedRevision,idempotencyKey}`. Создает `compose-resume` только при доказанной остановке, ошибке активации с подтвержденным отсутствием работающего опубликованного получателя и свежем подтверждении изоляции или остановки получателя без портов. Неизвестная активация блокирует возобновление до явной проверки состояния. Под общей блокировкой восстанавливаются записанные политики restart, работавший набор и таймер источника. Автоматического выполнения нет.

## 5 Сохраняемые данные и восстановление

Неизменяемый набор `rolypolyops-compose-v1` содержит манифест с serviceId, repositoryId, capture operationId, отпечатком источника, платформой, хешем производной конфигурации запуска, идентификаторами и хешами образов, уникальными зарезервированными псевдонимами, описаниями подключений/configs/secrets, ограничениями размера и числа файлов, SHA256. Полная разрешенная частная модель находится только в зашифрованном наборе и локальной регистрации с доступом root. Метки restic включают `rolypolyops-compose` и `service:<UUID>`. Агент и панель выбирают точный полный идентификатор снимка и проверяют внутри идентичность сервиса и репозитория. Наличие чужого снимка в том же репозитории не разрешает его восстановление.

Сохраняются все объявленные постоянные именованные тома, подключения файлов и каталогов, файловые configs/secrets, окружение и точные образы. Исполняемые сценарии из архива не запускаются. Доверенный закрепленный вспомогательный образ Python/GNU-tar подключает только выбранные данные и промежуточные каталоги, без сети, с корневой системой только для чтения и ограниченными полномочиями и ресурсами. Чтение Docker Mountpoint напрямую запрещено: используются обычные подключения томов Docker. Вспомогательный образ сохраняется для автономного восстановления. Экспортируемые образы получают зарезервированные псевдонимы по содержимому, чтобы загрузка не перезаписала метки чужого приложения. Несовпадение платформы отклоняется до загрузки и запуска.

До извлечения или загрузки проверяются внешние наборы и вложенные архивы ДАННЫХ: запрещены абсолютные пути, обход каталогов, дубликаты, устройства/FIFO/сокеты, родительские символьные ссылки, внешние символьные и жесткие ссылки, setuid/setgid/capabilities и опасные xattrs. Поддерживаются числовые UID/GID, права, время и безопасные внутренние ссылки. Сохраняются безопасные user.* xattrs и числовые POSIX ACL. Security.*, trusted.* и неизвестные влияющие на исполнение атрибуты отклоняются без незаметной потери. Квоты: до 100000 файлов на архив, до 256 ГиБ логических данных на сервис, путь до 4096, глубина до 64. Недостаток резерва места для промежуточных данных, образов и результата отклоняется до изменений. Неподдерживаемые атрибуты отклоняются явно. Извлечение использует свежий собственный подключенный к контейнеру каталог без других записываемых подключений сервера. Хеши и атрибуты проверяются до запуска приложения.

Восстановление создает уникальные проект и локальные тома, свежие места bind/config/secret с согласованной заменой общих ссылок. Разрешенные user, command, environment, readonly, healthcheck, ограничения ресурсов и безопасности сохраняются. Удаляются исходные container_name, build, restart, фиксированные имена и адреса сетей, все опубликованные порты изолированного режима. Допустимы только новые собственные внутренние сети с изолированным режимом шлюза IPv4/IPv6. Идентичность образа: хеш конфигурации одной платформы и OS/architecture, при необходимости variant. Отображаемого ID Docker или изменяемой метки недостаточно. Сохранение и загрузка явно учитывают платформу. Байты манифеста и конфигурации архива доказывают хеш. Получатель проверяет его после загрузки через inspect при эквивалентности либо явный экспорт нужной платформы и проверяет применение именно этого локального образа каждым контейнером. Недоказанная идентичность дает `image_identity_unverified`. До `isolated_ready` сравниваются идентичность образов, владение подключениями, хеши конфигурации и данных, действительная изоляция и здоровье. HTTP проверяется закрепленным помощником в изолированной сети, без произвольных docker exec команд оболочки. Вывод healthcheck и журналы не возвращаются панели.

## 6 Надежность и операции

Все намерения, остановленный набор, обязательство возобновления, собственные ресурсы и окончательные доказательства проходят fsync до зависимого эффекта. Общий flock сервера разделяется заданиями API, таймерами и восстановлением источника. У каждого зарегистрированного источника надежно записано состояние `running`, `capture_stopped`, `fenced` или `unknown`. Сохранение, таймер, расписание, остановка, возобновление и восстановление проверяют его под общей блокировкой. Таймер и сохранение отклоняют fenced/unknown. Остановка возвращает busy при конкуренции с сохранением и не присваивает его обязательство возобновления. Ошибка до доказанной остановки восстанавливает прежние политики, таймер и работающий набор, если это проверяемо. Иначе состояние неизвестно. Частичная активация исследуется по точным ресурсам и журналам: работающий здоровый зарегистрированный источник может быть принят как active или active_unprotected; доказанно изолированный получает ошибку; смешанное или непроверяемое состояние остается неизвестным. Busy до эффектов является повторяемой ошибкой `operation_busy`. Интерфейс предлагает повтор, таймеры повторяют без второй параллельной мутации. При запуске и периодически агент возобновляет только контейнеры, остановленные этим сохранением, проверяя неизменность ID/проекта/конфигурации. Намеренный compose-stop никогда не возобновляется. Ошибка перезапуска видна и блокирует ложный успех копии. Модули расписания запускают общий модуль с serviceId/state, только root, с теми же блокировками и данными доступа. Таймеры тестового приложения сохраняются.

Идентичность и доказательства работы таймера надежно сохраняются и без панели. Агент сообщает результаты и точные точки при подключении без выдуманного задания панели. Автоматическое удаление старых копий отсутствует. Неуспешная передача возобновляет источник, сохраняет диагностические сведения без секретов и разрешает явное новое сохранение. Таймаут или потерянный результат неизвестны до проверки. Слепой повтор запрещен. Очистка проверяет метки операции, каталоги и подключения; отклоняет текущие источники, активные восстановления, поврежденные записи владения и конфигурации, пересечения защищенных путей.

## 7 Приемка

Новая отдельная группа на источнике B содержит именованный том, обычное подключение вне проекта, значения env-file, файловые config и secret, закрепленный локально собранный образ и фактическое доказательство здоровья и данных. Через формы мастер подключает свежие выделенные REST и S3-совместимые испытательные репозитории без правки файлов для сервиса. Он импортирует, сохраняет, восстанавливает на A, проверяет значения данных, хеши, владение и права, действие env/config/secret и образы. Сохраненная копия переживает перезапуск и безопасно удаляется. Управляемая активация останавливает источник, открывает только выбранные порты, меняет источник и таймер, после чего копия с A восстанавливается на B. Тестовые страницы, таймеры, репозиторий и посторонние сервисы сохраняют исходное состояние. Неподдерживаемый проект и неверный пароль дают объяснимые ошибки до мутаций.

Проверяются nonce/CSRF/Origin, изменение источника, опасные подключения и поля модели, неверные сервис/репозиторий/снимок, ссылки/специальные файлы/квоты архивов, отсутствие контрольных секретов в SQLite/WAL/заданиях/журналах/хранилище браузера, реальные ограничения TLS/DNS прокси, восстановление после прерывания источника, повторная доставка, перезапуск панели и агента, занятые ресурсы, частичная активация, потеря ответа подключения и запрет очистки источника. Проверки модулей, настоящий Docker, браузер, перенос каталога и действующий выпуск разделяются. Неиспытанные CI, базы, провайдеры, ОС и архитектуры явно остаются неизвестными.

Первый закрепленный помощник: `python:3.12-slim-bookworm@sha256:e697c81897302a4c4333bade000d98038fbb21eb064f8ee1fd42d02ebcd9d337`, официальный многоплатформенный индекс. В каждом наборе записываются фактические платформа и хеш конфигурации. Старый источник после активации виден как остановленные устаревшие сохраненные данные, никогда не удаляется автоматически. Нет проверки приложения: `setupState:unverified`, без полной готовности. Общая блокировка неизвестного результата объясняет запрет операций тестового приложения.

## 8 Уточненные граничные правила

- Повторный compose-stop уже остановленного источника идемпотентно проверяет остановку, сохраняет ПЕРВЫЕ исходные политики, работающий набор и таймер, выдает новое доказательство. Текущие политики no не заменяют оригиналы.
- Active_unprotected относится к защите сервиса. Само восстановление имеет state active. SetupState: configuring, registered, backup_required, restore_required, schedule_required, unverified, complete, moving, active_unprotected, attention_required. Только complete означает полную готовность.
- Complete и activate требуют restore.nodeId, равный текущему service.recoveryNodeId и отличный от sourceNodeId. Замена получателя является явным изменением владельца со свежим подключением хранилища.
- ExpectedRepositoryId берется из надежного успешного результата источника и сохраняется в параметрах получателя ДО первой отправки. Верхний compose-restore snapshotId равен parameters.snapshotId.
- Закрытие из-за failed/unknown родителя имеет приоритет над сроком пакета; дочернее не отправляется. Иначе срок проверяется агентом до эффектов конфигурации и дает failed/envelope_expired. Успешное локальное доказательство проверяется без расшифровки просроченного пакета.
- Намерение init связывает выделенное место, requestId, поколение и проверочное значение пароля. RepositoryId заранее не назначается. Полученный ID принимается только успешным attach относительно намерения и записанного положительного доказательства пустоты.
- Create использует видимое новое место с storageId. Для REST итоговый точный URL равен базовому endpoint с добавленным UUID. Attach использует явно указанный существующий URL. Открытые сведения и зашифрованное содержимое несут один итоговый endpoint. Prepare возвращает итоговые сведения до шифрования. S3 аналогично выделяет новый префикс внутри выбранного базового. Исходно заполненное место отклоняется.
- Доверенный установщик получает закрепленный вспомогательный образ при его отсутствии на источнике. Сохранение не загружает незаметно изменяемый образ. Получатель до загрузки даже сохраненного помощника проверяет на сервере набор, архивы, модель и хеши. Восстановление ничего не загружает из сети.
- Изолированные для расследования операции означают существующие неразрешенные сообщения потерянных операций и блокировки переполнения. Все общие и тестовые отправки соблюдают эту общую блокировку.
- После успешной активации прежний источник становится recoveryNodeId. Получатель сохраняет допустимую исходную политику restart из снимка. Старый источник остается явно остановленным и устаревшим, с данными и отключенным таймером. Автоматического удаления и возврата нет.
- Таймеры создают надежные локальные ID и доказательства. Неизвестный результат появляется в аутентифицированном общем состоянии и создает блокировку собственных операций узла, не выдуманное успешное задание панели. Явная проверка разрешает журнал без повторного исполнения. Обычные результаты таймера обновляют историю точек с наблюдаемым происхождением.
- Исходные метки запуска сохраняются в зашифрованной оригинальной модели, но исключаются из созданного развертывания, чтобы не включить сторонние прокси и обновления. Продукт создает новые метки владельца и операции. Мастер раскрывает отсутствие переноса внешних маршрутов и автоматизации.
- Обычные безопасные user.* xattrs и числовые POSIX ACL сохраняются в местах для данных. Security.*, trusted.*, capabilities, setuid/setgid и неизвестные влияющие на исполнение атрибуты запрещены. Где обнаружимо, это проверяется до остановки и повторно в неизменяемом архиве.

Архивы образов являются отдельным классом. До docker load проверяются внешняя структура Docker/OCI, ограниченные обычные записи manifest/config/blob, объявленные хеши содержимого, точные платформа и конфигурация, ожидаемые псевдонимы. Слои образов никогда не извлекаются на сервер и тома данных. Символьные ссылки корневой системы контейнера, включая абсолютные внутри контейнера, права, setuid и штатные whiteout являются содержимым образа, обрабатываемым Docker. К ним не применяется правило архивов данных сервера; они не удаляются и не отклоняются незаметно. Безопасность обеспечивают проверенная идентичность исходного образа и ограничения подключений, полномочий и изоляции производного запуска. Неожиданные внешние ссылки, обход путей, объекты, неверный хеш и недоказанная идентичность отклоняются до загрузки.

До docker compose config каждый упорядоченный YAML/JSON исходный файл предварительно разбирается безопасным ограниченным синтаксическим разбором. Include, extends/provider сервиса и неподдерживаемые исполняемые теги отклоняются до команды Compose, способной разрешить или загрузить их. Явное локальное объединение нескольких файлов поддерживается. Самодельный разбор YAML регулярными выражениями запрещен. После защиты итоговую обычную модель формирует Docker.

После активации даже успешная firstBackup оставляет setupState restore_required до настоящего восстановления именно этой точки нового источника на новом recoveryNodeId. Интерфейс автоматически продолжает обычную последовательность restore/complete. После перезагрузки он предлагает завершить проверку без повторной активации. Вложенная проверенная activation.firstBackup является допустимым происхождением копии, без выдуманного задания панели. Нет копии нового источника: active_unprotected. Только соответствующее восстановление и фактическое расписание дают complete.

Сведения сервиса содержат постоянные безопасные последние activationGroupId и activation:{groupId,sourceStopJobId,targetJobId,status}. Сведения общих заданий содержат безопасные serviceId/storageId/restoreId/groupId/parentJobId по назначению, никогда полные параметры и пакеты. Это позволяет после перезагрузки возобновить только разрешенный источник и показать раздельную историю. Правила полномочий сохраняются.
