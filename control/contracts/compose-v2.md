# Compose service and storage contract, version 2

Status: implementation contract for 0.2.0; capabilities require acceptance before release. Existing demo APIs remain compatible. This contract concerns product behavior, not a delivery process.

Contract revision: 3 (clarifications of the accepted revision 2; no new capability claims). Earlier draft ambiguities are resolved by the rules below.

## 1 User outcome and boundaries

An owner selects an existing project on an enrolled Linux Docker host, connects a dedicated restic repository through the wizard, captures configuration, environment, images and persistent data, and restores an exact snapshot as a new project on another enrolled host. No lab.env, hand-written adapters, database commands or target directory preparation are required. The wizard completes only after an actual backup, matching restore and observed per-service schedule. Multiple services and repositories have distinct identities and histories.

Baseline: rootful Linux Docker 29+, Compose 2.24+ supporting canonical JSON, restic 0.16+, Python 3.11+, cryptography 41+ and PyYAML 6+ on agents. Controller remains standard-library-only. Installer checks prerequisites; on supported Ubuntu/Debian it can install missing restic/python3-cryptography/python3-yaml and Docker/Compose only when absent, without restarting or replacing existing deployments. Other systems get an exact prerequisite error, never a false connected state. Existing token enrollment remains the single privileged install step.

Scope: a whole local Compose project, currently running with one container per enabled service, local ordinary named volumes, ordinary data/config file or directory binds, file-backed configs/secrets, resolved runtime environment, already-built locally available images, and ordinary bridge networks. Capturing means bounded graceful stop of all its containers, copying data to an immutable local stage, resuming exactly the previously running set, then uploading the encrypted stage. The interruption is disclosed before confirmation. Application-level logical dumps and zero-downtime guarantees are not claimed.

Reject before stopping: privileged/host PID/IPC/network, devices, added capabilities, unsafe security options, docker socket or host-control mounts, external networks, anonymous/remote-driver volumes, volume driver_opts, replicas, unresolved dependencies/interpolation, unsupported executable model fields, unknown external writers, or changed configuration. Ordinary container root, read_only, cap_drop, no-new-privileges, user/group, command, entrypoint, environment, healthcheck, resource limits, depends_on, read-only mounts and local build provenance are supported. Build is removed from the derived runtime definition; exact running image IDs are saved instead. No build/pull during restore. Generated restores owned by this product cannot be imported as an unrelated source until activated/adopted by their owning service.

The owner confirms that the project is self-contained and has no writers outside its containers. The agent additionally rejects mount overlap with another running project's containers. Host-native writers cannot be discovered reliably; this assumption is visible, not silently claimed as verified.

## 2 Reuse and isolation

Reuse existing authentication, CSRF/Origin, SQLite, plans/jobs, UUID idempotency, nonces, agent incarnation and seen index, unknown-outcome holds, and reconciliation. Do not create another queue. Preserve the original demo profile, timers, data, UI routes and recovery behavior.

New persistent domain entities are storage, storage binding, Compose service and restore. Scope every generic job to serviceId/storageId/restoreId as applicable. Existing global serialization is retained for this release. Parent-child jobs may express dependencies; a child cannot dispatch until the required parent succeeded, and cannot infer success from its absence. A failed parent closes its undispatched child as status `failed`, stage `cancelled`, error `parent_failed`. An unknown parent closes the undispatched child as status `failed`, stage `blocked`, error `parent_unknown`. Neither ever requeues automatically, including after a later successful reconcile; the owner explicitly requests a new pipeline. The unresolved parent itself retains the global unknown hold.

Agent generic state is under its own state directory's managed/ subtree, except systemd units and temporary helper resources. Separate test instances use separate state. Registry credentials, full rendered Compose models, private keys and storage secrets remain root-only on the relevant hosts, never in controller SQLite, HTTP results, job receipts or logs. The controller stores only bounded sanitized metadata and sealed credential envelopes.

## 3 Discovery, credentials and storage

Agent status adds `compose` with `ready`, `error?`, `key:{id,publicKey,algorithm}`, `projects`, `storages`, `services`, `restores`, and `addresses`. publicKey is base64 DER SubjectPublicKeyInfo; id is its lowercase SHA256. algorithm is `RSA-OAEP-256+A256GCM`. Projects carry `id` (Docker project name), `name`, `fingerprint` (64 hex), `supported`, `reasons:[stable_code]`, `services:[{name,imageId,healthcheck,ports:[integer]}]`, `mounts:[{kind,target,label,readOnly}]`, estimatedBytes and architecture. services[].ports lists internal TCP target ports, never host published ports; UDP/SCTP publication candidates are excluded. No resolved environment values or host secret contents. Addresses are routable host IPs for showing the resulting address, never credentials. Bound counts and lengths: 20 projects, 20 containers/project, 100 mounts/project, 20 services per host and 8 repositories; oversized discovery is explicitly unsupported.

Discovery reads actual Compose labels for ordered configuration files/project directory and compares rendered model and actual containers/mounts/images. All commands use a fixed local Docker socket and explicit Compose files and project. Never source/eval application env files or trust their COMPOSE_*/DOCKER_* controls. The fingerprint binds canonical resolved model, container identity, image IDs and config/secret input bytes; it excludes mutable application data. Registration and each capture recheck it before stopping. A changed project requires the owner's visible re-import/update, not an automatic rebind.

Storage kinds: `rest` and `s3`. Metadata: `{id,name,kind,endpoint,bucket?,prefix?,region?}`. endpoint is a plain certificate-validated HTTPS origin/path with no userinfo, query, fragment or control characters. REST endpoint is the exact repository URL without `rest:`; S3 endpoint is HTTPS origin, plus a validated bucket and relative prefix. No local/filesystem/SSH/command backend in this release. Credentials: REST username/password; S3 accessKeyId/secretAccessKey and optional sessionToken. repoPassword is independent. Public TLS endpoints only; loopback, link-local, private/multicast/unspecified/metadata addresses are rejected. An exact-origin CONNECT proxy resolves and pins each connection to an allowed public IP, refuses all other authorities including redirects, and leaves end-to-end certificate validation to restic. Empty NO_PROXY prevents bypass. Do not disable TLS or rewrite /etc/hosts.

Agent creates persistent RSA-3072 key at first use with root-only permissions. Reinstall preserves it. Browser creates a fresh AES-256-GCM key and 12-byte IV for every envelope, wraps that key with RSA-OAEP SHA256/MGF1-SHA256, and uses a 128-bit GCM tag. Use cryptography on the agent and WebCrypto in the browser; no custom AES/RSA. Envelope:

`{v:1,algorithm:"RSA-OAEP-256+A256GCM",nodeId,keyId,storageId,requestId,bindingGeneration,mode,expiresAt,wrappedKey,iv,ciphertext}`

All binary fields are standard base64. Canonical UTF8 JSON (sorted keys, compact separators) of `{v,nodeId,keyId,storageId,requestId,bindingGeneration,mode,expiresAt,purpose:"storage"}` is AAD. Wrapped key is 384 bytes, IV 12 bytes, AES plaintext <=16KiB. ExpiresAt is a controller-issued UTC ISO time at most 15 minutes ahead. Expiry is checked at agent acceptance, not just enqueue. A child expired while queued fails `envelope_expired`; the wizard gets a fresh challenge and re-seals. Reconciliation reads durable local intent/binding proof and never needs or re-decrypts the envelope. Inner plaintext is `{metadata,repoPassword,credentials,bindingGeneration,requestId,mode}` and must exactly match the controller-approved metadata. requestId is a UUID persisted in the agent's accepted binding/version record. Controller-issued bindingGeneration is a positive monotonically increasing integer per storage/node. The agent refuses an older generation or a previously consumed requestId (a same-job durable receipt may be inspected without reapplication); the controller refuses a stale challenge. Higher generation replaces config only through the explicitly authorized connect request with no outstanding old binding work. Terminal job/plan parameters purge the sealed envelope, retaining its digest and safe intent metadata. The same request's durable receipt is reconciled without reinitialization. No raw secret values in browser localStorage/sessionStorage/IndexedDB or persistent controller state. UI retains them only during the wizard, offers a local recovery-kit download, and clears them on completion/logout.

The owner chooses `create` or `attach`. Attach verifies repository identity/password and never initializes. Create first positively proves absence of a repository config and emptiness of the dedicated backend prefix (REST known repository resources, or signed S3 ListObjectsV2). Authentication, TLS, bucket, transport or listing failures do not mean empty and never permit init. Persist empty-prefix proof and init intent before restic init. An unknown init outcome may be adopted only by attach-verifying the password and repositoryId against that exact recorded intent; otherwise remain unknown. Never reset/unlock/prune/forget or delete existing objects. Create uses a dedicated uniquely identified namespace, displayed before confirmation; unrelated populated prefixes are refused. First source binding creates the repository; subsequent recipient bindings attach to the exact returned repositoryId. Reconciliation checks local binding proof, not a blind second init. A failed password/TLS/bucket/permission check is a clear failed binding. New recipients use the same wizard and sealed credentials, never shell file edits.

## 4 Product API

All routes below inherit login/password-change gate, exact Origin, CSRF, JSON limits, stable errors and revision rules. APIs return metadata only. Client retains the identical request for retry with its UUID key; conflicting reuse is 409. New actions and scope fields are validated server-side and again on the agent.

GET `/api/overview` adds `storages`, `services`, `restores`; node status adds the sanitized `compose` object. Existing keys remain. Storage status shows repositoryId, per-node binding state and errors. Services show sourceNodeId, projectId/fingerprint, storageId, backupInterval, setupState, latestBackup/latestRestore, actual schedule and health scope. Snapshots are scoped by serviceId and repositoryId, not by whichever node happened to report them. Restores show id, serviceId, snapshotId, nodeId, state (`isolated_ready`, `active`, `failed`, `outcome_unknown`), checks and actual port mappings.

POST `/api/storages` body `{id,name,kind,endpoint,bucket?,prefix?,region?,expectedRevision,idempotencyKey}` creates metadata only. id is a client UUID so envelopes can bind it before upload. POST `/api/storages/{id}/prepare` body `{sourceNodeId,nodeIds,mode:"create"|"attach",expectedRevision,idempotencyKey}` returns an expiring durable challenge `{requestId,expiresAt,metadata,bindings:[{nodeId,key,mode,bindingGeneration}]}`. Only the source binding may create; recipients attach after the source proves repository identity. The UI seals each binding using this challenge. POST `/api/storages/{id}/connect` body `{requestId,bindings:[{nodeId,envelope}],expectedRevision,idempotencyKey}` creates a durable parent-first binding pipeline and returns `{jobs,storage}`. A single explicit wizard confirmation covers these bindings. A later call can add new nodes; existing successful bindings are retained unless a distinct authorized request rotates them. There must be no outstanding job for a binding being replaced.

POST `/api/services` body `{id,name,sourceNodeId,recoveryNodeId,projectId,fingerprint,storageId,backupInterval,exclusiveWriters:true,healthCheck?:{service,port,path,expectedStatus},expectedRevision,idempotencyKey}` creates a service and a `compose-register` job, returning `{service,job}`. Storage must already be connected on the source and chosen recovery node. Name is bounded plain text, IDs UUIDs, interval 15min/hourly/daily. projectId/fingerprint must match fresh supported discovery. healthCheck is HTTP only, no URL/host/header/shell; service belongs to project, port1..65535, relative path starts / without controls, expectedStatus 100..599. Rendered config and secrets never come from the browser. Updating an existing service uses the same explicit import with its current expectedRevision and no active work; no silent overwriting of registration.

Use existing POST `/api/plans`, POST `/api/jobs` and GET `/api/jobs/{id}` for generic operations; parameters include serviceId and scope and never shell text. Generic actions:

- `storage-configure`: internal binding jobs, `{storageId,metadata,envelope,mode,expectedRepositoryId?}`.
- `compose-register`: internal import job, `{serviceId,projectId,fingerprint,storageId,backupInterval,exclusiveWriters,healthCheck?}`.
- `compose-backup`, `compose-verify`: source/connected eligible node respectively, `{serviceId,storageId}`. Verify runs a full `restic check --read-data` for that bound repository, without claiming application correctness or creating a snapshot.
- `compose-restore`: chosen destination with connected binding, exact canonical top-level snapshotId and parameters `{serviceId,storageId,snapshotId}` (the two IDs must match). It retains an isolated new copy; restoreId equals jobId.
- `compose-remove`: `{serviceId,restoreId}`; only an isolated owned restore can be removed. An active copy cannot be removed through this action.
- `compose-schedule`: source only, `{serviceId,interval}`. Saves/applies a per-service systemd timer, not the old demo timer.
- `compose-stop`: internal source-fencing job for explicit controlled activation, `{serviceId,fingerprint}`.
- `compose-activate`: internal target job following successful stop, `{serviceId,restoreId,sourceStopJobId,interval,ports:[{service,target,published,hostIp,protocol:"tcp"}],allowEgress:true}`.

POST `/api/services/{id}/complete` `{restoreId,expectedRevision}` requires source registration, fresh connected bindings, fresh successful compose-backup + exact matching compose-restore on the selected other node with required data/image/runtime/health checks, actual enabled timer matching interval, and no active/unknown/quarantined operations. A no-health-check app is shown as started but unverified and cannot receive full readiness. health scope is explicit (Docker health/HTTP); no claim of arbitrary database business correctness.

POST `/api/services/{id}/activate` body `{restoreId,ports,allowEgress:true,acceptSnapshotLoss:true,expectedRevision,idempotencyKey}` creates the source stop -> target activation pipeline after explicit plan confirmation and returns {activationGroupId,jobs}. Only a successfully isolated restored copy of this service qualifies. The plan displays snapshotTime, age and the data-loss window, and requires `acceptSnapshotLoss:true`: changes made on the source after that selected snapshot will not appear on the destination. It is explicitly a historical restore, not a live migration/final-delta capture. "Fresh data" means bytes checked against that snapshot before first app startup; subsequent normal startup writes are not represented as identical backup bytes. This is an operator-requested controlled move, not automatic failover. Source must be connected and stop proof must be real; unreachable source is refused. Source timer is disabled and original restart policies are set to `no` before stopping. Target activation preserves its fresh data, uses only mapped chosen free TCP ports, allows requested network egress, and never adopts external/shared host resources. On verified activation the same service identity and repository history move to the target; target registers the owned generated project, becomes the new backup source and enables its per-service timer. It immediately attempts the first backup from the new source. The move/protection is complete only when this backup succeeds; a verified running destination with failed backup is `active_unprotected` and retains the new source authority, never a green protected service. Retry backup/configure through the UI; do not resume the old source. Old source stays stopped with timer disabled. Unknown/partial activation never automatically resumes the source. No Cloudflare/DNS, Caddy routing, provider fencing or automatic failback. Display actual IP/port and the limit that upstream firewall/TLS/DNS are outside this operation.

Existing POST `/api/jobs/{id}/reconcile` inspects exact generic operation journals/resources; never runs a mutation again based solely on lost receipt. Unknown operation and missing-catalog holds apply globally to generic and demo actions alike. Existing orphan inspection must dispatch generic scope inspection when present and never use demo cleanup rules for it.

Before dispatching activation the controller checks a durable successful source stop record matching serviceId, source fingerprint, assigned incarnation and sourceStopJobId. Trust in this check assumes an uncompromised controller. Snapshot time and loss acceptance are immutable parts of the plan. UDP/SCTP publication is explicitly unsupported; every published mapping is selected by the owner.

POST `/api/services/{id}/resume-source` `{activationGroupId,expectedRevision,idempotencyKey}` creates `compose-resume` only when a stop is proven, activation failed with verified absence of any online target, and the target is freshly confirmed isolated/stopped with no ports. An unknown activation blocks resume until explicit inspection proves target state. It restores the source's previously recorded restart policy, running set and timer under the shared lock; it never runs automatically.

## 5 Capture and restore artifacts

Immutable service bundle format `rolypolyops-compose-v1`: manifest with serviceId, repositoryId, capture operationId, source fingerprint, platform, derived runtime config digest, image IDs/digests and unique reserved aliases, mounts/config/secret artifact descriptors, size/file-count limits and SHA256 values. The fully resolved private model is only in this encrypted bundle and root-local registration. Restic tags include `rolypolyops-compose` and `service:<UUID>`; agent/controller select an exact full snapshot ID and verify both service and repo identity inside it. Never restore another service merely because its snapshot exists in the repository.

Capture all declared persistent named volumes and file/directory binds, file-backed configs/secrets, runtime env and exact images. No executable scripts from an archive. A trusted pinned Python/GNU-tar helper image mounts only the selected data and staging dirs, with network none, readonly root and bounded capabilities/resources. Do not read Docker's host volume Mountpoint directly; use ordinary Docker volume mounts. Save helper image with the bundle for offline restore. Locally retag exported images to reserved content-derived aliases so loading cannot overwrite another application's tags. Reject platform mismatch before load/start.

Validate package envelopes and nested DATA tar entries before extraction/load: no absolute/traversal/duplicate names, devices/FIFO/sockets, symlink parents, external symlinks/hardlinks, setuid/setgid/capabilities or unsafe xattrs. Support numeric UID/GID, permissions, timestamps and safe internal links. Preserve safe user.* xattrs and numeric POSIX ACLs; reject security.*, trusted.* and any unrecognized execution-affecting metadata rather than silently dropping it. Quotas: <=100000 files per archive, <=256GiB logical bytes per service, paths<=4096, depth<=64; reject before mutations if local free-space reserve cannot fit staged data/images and restored contents. Reject unsupported metadata explicitly rather than silently losing it. Extraction uses a fresh owned container-mounted destination with no other host write mounts. Hash/metadata verification occurs before the app starts.

Restore creates a unique project, unique local volumes and fresh bind/config/secret locations, remapping shared references consistently. Preserve allowed user, command, environment, readonly flag, healthcheck and resource/security restrictions. Remove source container_name, build, restart policy, fixed network names/addresses and all published ports for isolated mode. Only newly owned internal networks with isolated IPv4/IPv6 gateway mode. Identity is the single-platform image config digest plus OS/architecture (variant where relevant), not merely the Docker display ID or mutable tag. Save/load is platform-explicit. The image archive manifest/config bytes establish the digest; destination verifies it after load (inspect when equivalent, otherwise a platform-explicit verification export) and checks each actual container uses that verified local image. Unprovable identity fails `image_identity_unverified`. Compare image identities, mount ownership, config/data manifest hashes, actual isolation and health before recording `isolated_ready`. Probe HTTP using the pinned helper on the isolated network, not arbitrary docker exec shell commands. Healthcheck output/log values are not returned to controller.

## 6 Durability and operations

All intents, stopped-container set, resume obligation, owned resources and terminal proof are fsynced before their dependent effect. A generic per-host flock is shared by API jobs, timers and source-recovery. Every registered source has durable state `running`, `capture_stopped`, `fenced` or `unknown`. Capture, timer, schedule, stop, resume and recovery check it under the same lock. Timers/capture refuse fenced/unknown sources. Stop fails busy rather than racing a capture; it never steals its resume obligation. A stop failure before proven fencing restores original policies/timer/running state if verifiable; otherwise state becomes unknown. A partial activation is inspected through exact owned resources/journals; online+healthy+registered source may be adopted as active or active_unprotected; positively still-isolated may be marked failed; mixed/unverifiable state remains unknown. Busy before effects is `operation_busy` with no unknown claim; UI offers retry, timers retry without a second concurrent mutation. Agent startup/periodic recovery resumes only containers this capture stopped after checking unchanged IDs/project/config; it never resumes an intentional compose-stop source. Restart failure is visible and blocks a false successful backup. Schedule units invoke the generic module with the serviceId/state, root-only, using the same locks and credentials; existing demo units remain untouched.

Timer operation identity and proof are durable even without the controller. Agent reports their results and exact points on reconnect, with no fabricated controller job. No automatic retention deletion. Failed transfer resumes source, keeps diagnostic metadata without secrets and allows an explicit new capture. A timeout or lost execution outcome is unknown until inspected; no blind replay. Cleanup verifies operation labels, directories and mounts and refuses current sources/active restores, corrupt ownership/config records or overlapping protected paths.

## 7 Acceptance

A fresh non-demo fixture on source B includes a named volume, ordinary outside-project bind, env-file values, file config and secret, pinned local-built image and actual application health/data proof. Wizard connects fresh dedicated REST and S3-compatible test repositories via forms (no per-service host file edits), imports, captures, restores on A, and verifies data values, file hashes, ownership/modes, env/config/secret effects and images. Retained restore survives restart and is removed safely; a controlled activation stops the source, exposes only chosen ports, changes backup source/timer, and makes a subsequent backup from A usable on B. Existing demo pages/timers/repository and unrelated services retain baseline state. An unsupported project and bad credentials have explainable pre-mutation failures.

Test nonce/CSRF/Origin, source drift, unsafe mounts/model keys, wrong service/repository/snapshot, archive links/special files/quota, secret sentinel absence from SQLite/WAL/jobs/logs/browser storage, actual TLS/DNS proxy restrictions, source interruption recovery, duplicate delivery, controller/agent restart, occupied target resources, partial activation, lost binding reply and no-cleanup-of-source. Separate pure-module, real Docker, browser, migration and live release evidence. CI/other databases/providers/OS/architectures not tested must remain explicitly unknown.

The initial pinned helper is `python:3.12-slim-bookworm@sha256:e697c81897302a4c4333bade000d98038fbb21eb064f8ee1fd42d02ebcd9d337` (official multi-platform index). Actual selected platform/config digest is recorded in each bundle. The previous source remains visible as stopped/stale retained data after activation; it is never deleted automatically. Missing application health yields `setupState:unverified`, not a complete protected service. A global unknown hold explains that it also blocks demo operations.

## 8 Clarified edge semantics

- An already-fenced compose-stop is an idempotent ensure-fenced operation: verify current state, keep the FIRST recorded original policies/running set/timer, and issue a new operation proof. Never replace original policies with the current no policy.
- active_unprotected is a service-level protection state; the actual restore is active. setupState values are configuring, registered, backup_required, restore_required, schedule_required, unverified, complete, moving, active_unprotected, attention_required. Only complete is fully ready.
- For complete and activate, restore.nodeId must equal the current selected service.recoveryNodeId and differ from its sourceNodeId. A changed recipient is an explicit owner configuration update with fresh storage binding, not an inferred destination.
- ExpectedRepositoryId is learned from the source binding's durable successful result and filled/persisted in recipient params BEFORE first dispatch. The top-level compose-restore snapshotId and parameters.snapshotId must equal each other.
- Failed/unknown parent closure takes precedence over envelope expiry: that child never dispatches. Otherwise expiry at agent acceptance produces failed/envelope_expired before configuration effects. A successful local proof is inspected without decrypting an expired envelope.
- Init intent binds dedicated namespace, requestId, generation and a password verifier; no repository ID can be preassigned. Adopt a learned ID only through successful attach using that intent and a recorded positive empty-prefix proof.
- Create uses a visible new namespace containing storageId. For REST the final exact URL is base endpoint plus that UUID; attach uses the explicitly supplied exact existing repository URL. Metadata and sealed plaintext carry the same final repository endpoint. Prepare returns the finalized metadata before the browser seals it. S3 similarly uses a visible dedicated prefix beneath the selected base prefix in create mode. An initial populated namespace is refused.
- The trusted installer obtains the pinned helper if absent on the source; capture never silently pulls a mutable image. Destination performs host-side bundle/tar/model/digest validation before loading even the saved helper. Restore pulls nothing.
- Quarantined operations mean the existing unresolved orphan reports/overflow holds; all generic dispatch and demo dispatch respect the same hold.
- After successful activation the former source becomes the selected recoveryNodeId. Target preserves the original allowed restart policy recorded in the snapshot. Old source remains visibly stopped/stale with retained original data and disabled timer. No automatic deletion or return.
- Timers produce durable local operation IDs/proofs. Unknown timer outcomes appear in authenticated generic status and create an own-node orphan/operation hold, never a fabricated successful controller job. Existing explicit inspection can settle that generic journal without replay. Normal timer results update service point history with observed provenance.
- Runtime labels supplied by the source are retained in the encrypted original model but omitted from the generated deployment to avoid activating host-side proxies/updaters. New owner/operation labels are generated by this product. The wizard discloses that external routing/automation integration is not reproduced.
- Ordinary safe user.* xattrs and numeric POSIX ACLs are preserved in data-only destinations. security.*, trusted.*, capabilities, setuid/setgid and unknown effect-bearing metadata are refused. These restrictions must be checked before source interruption where discoverable and again on the immutable archive.

Image archives are a separate artifact class: validate the outer Docker/OCI archive layout, bounded regular manifest/config/blob entries, declared content digests, exact platform/config identity and expected aliases before docker load. Never extract image layers onto the host or data volumes. Container-rootfs symlinks (including absolute in-container targets), modes, setuid files and native layer whiteouts are image contents handled by Docker, not host-data archive entries. They are not silently stripped or rejected by the host-data metadata rule. Safety is enforced by the verified source image identity and the derived runtime mount/capability/isolation restrictions. Unexpected outer links/traversal/objects, digest mismatch or unprovable identity still reject before load.

Before docker compose config, safely pre-parse every ordered source YAML/JSON file with bounded safe AST parsing. Reject include, service extends/provider and unsupported executable tags before any Compose command can resolve/fetch them. Local explicit multi-file merging remains supported; do not implement a handwritten YAML regex parser. Docker remains the final ordinary Compose model renderer after this guard.

After activation, even a successful firstBackup leaves setupState restore_required until that exact new-source point is actually restored on the new recoveryNodeId. The UI automatically continues this normal restore/complete flow after activation; on reload it offers finish validation without reactivating. The nested verified activation.firstBackup is valid captured backup provenance, not a fabricated controller job. Missing new-source backup remains active_unprotected. Only a matching restore plus actual schedule gives complete.

Service metadata exposes persistent safe latest activationGroupId and activation:{groupId,sourceStopJobId,targetJobId,status}; generic job metadata exposes safe serviceId/storageId/restoreId/groupId/parentJobId where applicable, never raw parameter/envelope bodies. This enables reload-safe guarded resume and scoped history; authorization is unchanged.
